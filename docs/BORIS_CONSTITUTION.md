# Конституция BORIS

Версия: 1.0 — 2026-09-10

## 1. Для чего этот документ

BORIS постоянно развивается. Бизнес-правила, алгоритмы, интерфейсы и модули МОГУТ и ДОЛЖНЫ меняться.

Неизменяемым является не конкретное правило, а порядок изменения системы: новое правило не появляется параллельно старому без явной версии, один факт не имеет нескольких хозяев, ошибка не исчезает молча, а новая версия не считается готовой без проверки старого поведения.

Главная цель: владелец не является оператором системы. Нормальный путь сбоя: DETECT -> DIAGNOSE -> SELF-HEAL -> VERIFY -> RETRY -> ESCALATE только когда автоматическое восстановление невозможно или требуется бизнес-решение владельца.

## 2. Два уровня правил

### 2.1 Конституционные правила

Это правила построения BORIS. Они меняются редко и только новой версией с объяснением причины.

### 2.2 Бизнес-правила

Это конкретная логика продукта: лимиты ставок, KPI, число писем, сценарии МОПа, правила реактивации, тарифы, расписания и т.д. Они могут меняться часто.

Каждое бизнес-правило должно иметь идентификатор/версию, область действия и понятный источник истины. Новая версия явно заменяет старую (`supersedes`), а не добавляется рядом скрытым `if`.

## 3. Конституционные правила

### CONST-01 — один источник истины

Для каждого важного факта существует один главный источник: бюджет, KPI, статус публикации, статус звонка, состояние сделки, оплаченный период, разрешение на действие. Представления и отчёты читают его, а не ведут параллельные копии истины.

### CONST-02 — один главный writer на одно действие

У действия, меняющего внешний мир или важное состояние, есть один канонический исполнитель. Другие модули могут запросить действие, но не должны тайно выполнять его вторым путём.

Примеры: изменение ставок, отправка клиентского сообщения, отправка email, публикация объявления, изменение телефонного lifecycle, списание денег.

### CONST-03 — никаких затенённых реализаций

В одном Python-модуле запрещены несколько top-level функций/классов с одинаковым именем. Если старая реализация нужна как слой новой, она получает явное имя `_legacy_*`, `_base_*`, `_vN` и явную ссылку.

### CONST-04 — ошибка бизнес-действия не исчезает молча

В критическом пути запрещено `except Exception: pass`. Любая попытка должна завершиться одним из нормализованных состояний: `OK`, `BLOCKED_POLICY`, `WAIT_EXTERNAL`, `RETRY`, `DEGRADED`, `FAILED_INTERNAL`.

Внутренняя ошибка обязательно получает лог/метрику/operation_id. Владельцу она показывается только после исчерпания безопасного self-heal.

### CONST-05 — штатный запрет не является аварией

Guard/лимит/отсутствие разрешения/ожидание внешнего сервиса не должны валить весь worker. Все вызывающие пути одинаково обрабатывают `ALLOW/BLOCK/WAIT/RETRY/FAIL`.

### CONST-06 — идемпотентность

Повтор одной бизнес-операции не создаёт дубль. Для внешних сообщений, денег, публикаций, звонков, генераций и очередей используется устойчивый idempotency/request key.

### CONST-07 — изоляция клиентов

Изменение/ошибка/данные одного account_id не меняют другого клиента. Любой multi-tenant запрос, кеш, очередь, lock и audit имеют account scope там, где он нужен.

### CONST-08 — внешний факт подтверждает внешняя система

`publish_requested` не равно `published`; `call_requested` не равно `connected`; `email_queued` не равно `sent`. Финальное состояние внешнего действия появляется после подтверждения провайдера или доказанного reconciliation.

### CONST-09 — безопасное состояние при неопределённости

При stale/неполных/противоречивых данных разрушительные и денежные действия fail-closed. Бесплатная и безопасная работа по возможности продолжается.

### CONST-10 — схема БД меняется миграциями

Новые таблицы/колонки/ограничения оформляются versioned migration. Рабочий request/worker не должен становиться местом появления новой схемы. Миграция имеет checksum, порядок, блокировку, запись факта применения и совместимость с откатом кода.

Существующий runtime-DDL считается техническим долгом и уменьшается постепенно; его количество не должно расти.

### CONST-11 — production не является общей черновой папкой

Обычная разработка проходит через development patch/worktree -> tests -> acceptance -> deploy. Emergency hotfix допустим только с preflight, backup/rollback, минимальным scope, проверкой и записью результата. Нельзя иметь двух независимых авторов, одновременно переписывающих один критический scope.

### CONST-12 — баг превращается в постоянный regression test

Исправление без теста, воспроизводящего класс бага, не закрывает задачу, если такой тест технически возможен.

### CONST-13 — проверяется весь затронутый граф

Новая функция проверяется сама и вместе с соседями. Изменение CRM проверяет потребителей CRM; изменение общей модели/авторизации/денег/очередей получает расширенный regression scope.

### CONST-14 — тесты проверяют переходы, а не только наличие guard

Недостаточно доказать, что защита существует. Проверяются все основные callers и ответы `ALLOW/BLOCK/WAIT/RETRY/FAIL`.

### CONST-15 — план != факт

Scheduler active, job queued, request accepted и кнопка нажата не являются выполнением. Для обязательств хранится план, попытка, подтверждённый факт, причина отставания и следующая попытка.

### CONST-16 — самовосстановление не скрывает первопричину

Self-heal может перезапустить worker, повторить безопасную операцию, снять stale lock или reconcile состояние. Он не превращает неуспешное действие в зелёное и не маскирует неизвестную ошибку.

### CONST-17 — один release имеет точную идентичность

Должны быть известны версия/commit/source generation и время выкладки. После deploy выполняются health/smoke/regression проверки. Неуспешная выкладка автоматически откатывается там, где это безопасно.

### CONST-18 — изменение правила версионируется

Правило меняется так: `vN active -> vN+1 proposed -> tests -> active`; старая версия становится `superseded`, история решения остаётся. Запрещено тихо менять смысл одного и того же rule_id без версии/следа.

### CONST-19 — AI предлагает, код охраняет жёсткие пределы

AI может классифицировать, советовать и планировать. Денежные, tenant, permission, idempotency, privacy и другие жёсткие ограничения проверяются детерминированным кодом перед действием.

### CONST-20 — владелец не оператор

Если проблема техническая и исправима системой, BORIS обнаруживает, диагностирует, пытается восстановить и проверяет сам. Владельцу эскалируется только то, что действительно требует денег, документов, доступа, юридического/коммерческого выбора либо необратимого решения.

## 4. Обязательный жизненный цикл любой задачи разработки

1. Зафиксировать конечный пользовательский результат и критерии приёмки.
2. Определить затронутые модули, writers, source of truth, БД и внешние зависимости.
3. Снять preflight текущего production-state и не путать старые ошибки с новыми.
4. Создать возможность отката для рискованной правки.
5. Найти первопричину, а не симптом.
6. Сделать минимальное связное изменение.
7. Проверить синтаксис/сборку.
8. Прогнать новый regression test.
9. Прогнать весь затронутый набор тестов; штатный backend patch также проходит общий pytest baseline/post-regression.
10. Проверить runtime и реальный пользовательский сценарий без лишних платных вызовов.
11. Проверить соседние модули по dependency graph.
12. Выполнить deploy через канонический owner.
13. Выполнить smoke/health после deploy.
14. Записать результат и только после доказательств считать задачу закрытой.

## 5. Definition of Done

Задача НЕ готова, если есть только написанный код или зелёная компиляция.

Готово означает одновременно:
- критерий пользователя выполнен;
- первопричина устранена;
- нет нового параллельного writer/source of truth;
- есть regression-защита;
- старые затронутые тесты не ухудшились;
- runtime работает;
- реальный сценарий подтверждён настолько, насколько это можно сделать безопасно;
- ошибка видима/самовосстанавливаема;
- rollback/backup понятен для рискованного изменения;
- статус plan/fact отражает реальность.

## 6. Как владелец ставит задачу

Владельцу не нужно перечислять файлы, функции, SQL и команды. Достаточно пяти вещей:

1. **Кому/где:** клиент или общий BORIS, модуль/экран если известен.
2. **Проблема:** что сейчас происходит неправильно.
3. **Как должно быть:** конечный результат простым языком.
4. **Жёсткие ограничения:** что нельзя делать/ломать/тратить.
5. **Приоритет/срок:** срочно P0/P1 или обычное улучшение.

Пример:

> Мария, Авитолог. Сегодня снова снизились ставки, хотя план лидов не выполнен. Нужно, чтобы BORIS сам держал ставки по актуальному правилу и больше не возвращал старую логику. Нельзя превышать дневной бюджет и красную цену лида, нельзя снимать объявления. Найди первопричину, исправь, добавь regression, проверь остальных клиентов и production. Я не оператор.

Этого достаточно. Исполнитель BORIS обязан сам определить файлы, зависимости, тесты, rollback и соседний regression scope.

## 7. Приоритеты

P0 — клиент прямо сейчас не получает оплаченную услугу / production недоступен.
P1 — результат неверный, тихо не выполняется или требует ручного удержания.
P2 — нет detect/self-heal/verify/retry для уже понятного класса сбоя.
P3 — UX мешает работе.
P4 — улучшение/косметика/рефакторинг без текущего влияния на услугу.

Работа идёт P0 -> P1 -> P2. P3/P4 не вмешиваются в критический путь.

## 8. Формат изменения правил

Минимальная карточка правила:

```text
rule_id: <стабильный идентификатор>
version: <N>
module: <модуль>
scope: global/account/feature
status: proposed|active|superseded|disabled
source_of_truth: <где хранится факт>
writer: <кто единственный меняет состояние>
inputs: <какие данные нужны>
result_states: ALLOW|BLOCK|WAIT|RETRY|FAIL
hard_guards: <что нельзя нарушать>
supersedes: <предыдущая версия или none>
regression_tests: <какие тесты защищают>
reason: <почему версия изменилась>
```

## 9. Запрещённые анти-паттерны

- второй scheduler «на всякий случай»;
- второй writer одной ставки/сообщения/публикации;
- второй storage одного факта без явной роли cache/read-model;
- `except Exception: pass` в бизнес-цепочке;
- статус `готово` до внешнего подтверждения;
- изменение production сразу несколькими независимыми авторами одного scope;
- новый `CREATE/ALTER TABLE` внутри обычной бизнес-функции;
- исправление симптома без выяснения, кто и почему вернул плохое состояние;
- удаление/перезапись истории правила вместо `supersedes`;
- тест только на наличие строки/guard без проверки поведения callers, когда поведенческий тест возможен.

## 10. Главная короткая формула BORIS

**Один факт -> один источник истины. Одно действие -> один writer. Новое правило -> новая версия. Любой баг -> regression. Любое действие -> подтверждённый факт. Любой технический сбой -> detect -> diagnose -> self-heal -> verify -> retry, и только потом владелец.**
